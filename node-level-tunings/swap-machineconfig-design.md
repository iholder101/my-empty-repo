## Context

When Kubernetes NodeSwap is enabled on OpenShift nodes running KubeVirt (OpenShift
Virtualization), the kernel's default memory watermarks are too narrow
(`watermark_scale_factor=10`, i.e., 0.1% of managed memory). This means kswapd barely
runs before kubelet's eviction threshold is hit, causing unnecessary pod evictions even
when swap space is available.

The kubelet eviction manager computes `memory.available = capacity - workingSet` using
only physical RAM -- it does not consider swap. When physical memory drops below the
eviction threshold (default 100Mi), pods are evicted regardless of available swap.

The goal is to configure the node so that three safety mechanisms fire in the correct
order with meaningful gaps:

```
HIGH watermark    ── kswapd goes back to sleep
    |  kswapd working range
LOW watermark     ── kswapd wakes up, begins background reclaim (swap-out)
    |  CRITICAL: kswapd runway before eviction
Eviction threshold── kubelet evicts pods
    |  safety margin
MIN watermark     ── direct reclaim (process stalls)
    |
OOM Killer        ── last resort
```

Additionally, system services (kubelet, CRI-O) in `system.slice` must be protected from:
- Being swapped out (would cause node NotReady)
- IO starvation from swap IO generated by workload pods
- CPU starvation from kswapd activity during swap storms

## Design: Single MachineConfig

### Components

| # | Component | Method | Purpose |
|---|-----------|--------|---------|
| 1 | Adaptive watermark script | File + oneshot service | Compute and apply `watermark_scale_factor` |
| 2 | system.slice drop-in | Systemd slice drop-in | `MemorySwapMax=0`, `IOWeight`, `CPUWeight` |
| 3 | kubepods.slice drop-in | Systemd slice drop-in | `IOWeight` (low priority) |
| 4 | IO latency discovery script | File + oneshot service | Discover swap/root block devices, apply `IODeviceLatencyTargetSec` dynamically |

### What is NOT configured (and why)

| Parameter | Reason |
|-----------|--------|
| `vm.min_free_kbytes` | Left at kernel default; it is a safety reserve for atomic allocations and should not be repurposed for watermark positioning |
| `vm.swappiness` | Left at kernel default (60); appropriate for mixed workloads |
| `MemoryMin` / `MemoryLow` on system.slice | Not used; swap protection via `MemorySwapMax=0` and watermark ordering are sufficient |

## Algorithm: Adaptive `watermark_scale_factor`

The script (embedded in the MachineConfig below) computes a `watermark_scale_factor`
so that LOW = eviction + runway. Key design points:

- `min_free_kbytes` is left at kernel default.
- `watermark_scale_factor` controls the gap between watermarks (gap = `managed * scale / 10000`;
  LOW = MIN + 1 gap). Setting scale so that LOW > eviction guarantees kswapd activates
  before eviction.
- The runway (`max(256MiB, 1% RAM)`) scales with node size to match higher aggregate
  memory consumption rates on larger nodes.

### Computed watermarks across node sizes and eviction thresholds

The runway (LOW − eviction) is ~1% of RAM for all node sizes and is independent of
the eviction threshold — only node size determines the kswapd headroom.

### Edge cases and limitations

| Scenario | Issue | Handling |
|----------|-------|---------|
| Node > 660 GiB with eviction = 100 Mi | Kernel default `min_free_kbytes` may exceed eviction threshold (MIN > eviction) | Script logs a warning and recommends raising the eviction threshold. LOW >> eviction still holds so kswapd ordering is maintained |
| Small node (32 GiB) with large eviction (1 GiB) | HIGH reserves 8.2% of RAM | Documented limitation; the kernel forces equal spacing between MIN/LOW/HIGH so HIGH cannot be capped independently of LOW |

## IO Protection: `io.latency`

`io.latency` is a block-layer rq-qos controller that works with ANY IO scheduler
including `none` on NVMe. It explicitly accounts for all IO types including
swap IO.

The protection mechanism works at the peer level: when system.slice's IO latency exceeds
its target, the kernel throttles kubepods.slice (which has a looser target). Both peers
must have targets set **on the same block device** for throttling to occur.

### Dynamic device discovery

Because `io.latency` targets are per-device and swap is typically on a dedicated disk
(not the root device), the targets cannot be hardcoded in static systemd drop-ins.
Instead, a boot-time script discovers the relevant block devices and writes transient
drop-ins under `/run/systemd/system/`:

1. Parse `/proc/swaps` to find active swap devices (skipping zram).
2. Resolve device-mapper chains via `/sys/class/block/<dev>/slaves` recursively.
3. Resolve partitions to whole-disk via `/sys/class/block/<dev>/partition` + parent link.
4. Also resolve the root device (`findmnt -n -o SOURCE /`) through the same chain.
5. Deduplicate, then write:
   - `/run/systemd/system/system.slice.d/20-io-latency.conf` with
     `IODeviceLatencyTargetSec=<dev> 5ms` for each device.
   - `/run/systemd/system/kubepods.slice.d/20-io-latency.conf` with
     `IODeviceLatencyTargetSec=<dev> 50ms` for each device.
6. `systemctl daemon-reload`.

Using `/run/` means the drop-ins are cleared on reboot and re-created by the script on
next boot, so they always reflect the actual device topology. This also handles nodes
with multiple swap devices (e.g. striped LVM, multiple swap partitions).

## IO Weight: `IOWeight`

`IOWeight` provides proportional IO fairness on devices using the BFQ scheduler.
system.slice gets a higher weight (800) so kubelet and CRI-O are prioritized over
kubepods.slice during IO contention. This complements `io.latency` which is
latency-based and works on all schedulers including `none` on NVMe - `IOWeight` adds
weight-based fairness where the scheduler supports it.

## CPU Protection: `CPUWeight`

During swap storms, kswapd consumes significant CPU. A higher `CPUWeight` on system.slice
ensures kubelet and CRI-O win CPU contention. This is universal, requires no device
discovery, and is always effective on cgroup v2.

## Deployment

The MachineConfig is authored as a [Butane](https://coreos.github.io/butane/) file
(`99-swap-node-tuning.bu`) and transpiled into a deployable MachineConfig YAML.

Butane is used because raw Ignition (which MachineConfig embeds) does not support
`inline` file contents — it requires `source` with data URIs, making embedded scripts
unreadable. Butane accepts `inline` and compiles it into the correct Ignition format.

To generate and apply:

```bash
./generate-machine-config.sh
oc apply -f 99-swap-node-tuning.yaml
```

### Known limitation: file-backed swap

The IO latency discovery script currently only detects **partition-backed** swap
(entries in `/proc/swaps` with type `partition`). File-backed swap (type `file`, e.g.
`/var/tmp/swapfile`) is not yet resolved to its underlying block device. On nodes using
file-backed swap, the `io.latency` protection will not be applied. The remaining
protections (watermark tuning, `MemorySwapMax=0`, `IOWeight`, `CPUWeight`) are
unaffected and fully functional.

## Summary

This single MachineConfig provides three layers of protection:

1. **Watermark ordering** (adaptive script): Guarantees kswapd activates before kubelet
   eviction fires, giving swap time to remedy memory pressure before pods are evicted.

2. **System.slice swap isolation** (`MemorySwapMax=0`): Prevents kubelet, CRI-O, and
   other system services from ever being swapped out, which would cause node NotReady.

3. **System.slice IO and CPU protection** (`IODeviceLatencyTargetSec`, `IOWeight`, `CPUWeight`):
   A boot-time script discovers all block devices backing swap and root, then applies
   `io.latency` targets dynamically via transient systemd drop-ins. This ensures
   protection works regardless of whether swap is on the root device or a dedicated disk.
   When kubepods.slice generates heavy swap IO, the kernel throttles it to protect
   system.slice IO latency. `IOWeight` provides proportional IO fairness on devices
   using the BFQ scheduler (no-op on NVMe with `none` scheduler). Higher CPU weight
   ensures system services win CPU contention during swap storms.
